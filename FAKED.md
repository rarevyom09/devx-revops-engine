# What I faked / what I'd do next

Living note. Updated as the build progresses.

## Faked / simulated
- **All data is invented.** People, deals, invoices, payments, timesheets and rates come from `src/lib/demo-data.ts`.
- **No Zoho integration.** Data enters via the Ingest tab (paste, CSV, quick form) instead of CRM/Books sync.
- **Variable pay at stake = 5% of invoice amount.** Invented rule; the real plan is unknown.
- **Rates are invented** (IN ₹2,000/h, SG ₹6,500/h), everything in INR. No FX handling.
- **No auth, no Row Level Security.** Single-user demo. All writes go through server routes using the Supabase service-role key; the browser never talks to the DB directly.
- **Partner handling is a flag only.** No MDF accounting or deal-registration logic.
- **Calendar quarters assumed** for the realization deadline (one constant in `src/lib/clawback.ts`). Indian FY quarters (Apr–Mar) cover the same three-month blocks, so deadlines are identical; only quarter labels change.
- **Clawback is per invoice**, summed per owner. Owner-quarter netting is not modelled.
- **60-day "at risk" window** and **30% margin floor** are invented thresholds.
- **As-of date on Clawback is a demo time machine**; payments after the chosen date are hidden.
- **Pass-through costs stubbed at ₹0** (no table). **No planned hours**: the "plan" is a target margin % (default 40%, editable).
- **Recurring deal price = monthly amount × term months** for margin and booked value.
- **Rates are flat per location**, not by role or seniority. Margin what-if hours are a browser-only simulation, never saved.
- **Deal Integrity has only been tested on 6 invented deals**; precision/recall on real CRM text is unmeasured.
- **Onboarding invoices are scheduled mock rows**: created on brief approval with `raised_on` = milestone due date (often future). Nothing is sent to Zoho Books.
- **Recurring billing schedules are generated by code**, not the AI (equal monthly invoices from first billing date). The AI only writes brief text. Deliberate: "AI drafts language, code owns the money schedule."
- **Seeded historical deals get no new invoices** on brief approval (they already have some); reconciliation would be manual.
- **Demo "today" is pinned to 2026-10-02** in Clawback and Onboarding so date checks are reproducible.
- **One-draft-per-deal and approve→invoice atomicity are enforced in app code**, not the database. Next: a partial unique index and a Postgres function so approval + invoice creation is one transaction.
- **Practice split ("double bubble")**: captured at approval as one split applied to every record from that description (open question: should a project and its retainer split differently?). Practice list (AI/Web/Cloud/Data) is invented. Practice-side variable pay is not computed; a missing split shows as an attribution leak.
- **Rep questions are answered in the tool by the ops lead on the rep's behalf.** There is no rep-facing form, Slack/email loop or notification yet; answers are saved on the analysis (`deal_analyses.rep_answers`) for audit. Each question is mapped by the AI to one platform field; a wrong mapping would put the answer in the wrong field, so every applied answer stays visible and editable before approval. Questions analysed before this feature are plain text and map to "note only".
- **Deal Pipeline stages are derived** from existing data (approval, brief, invoice dates, payments), not stored; no drag-and-drop. Home page and board share one data load (`src/lib/snapshot.ts`), so their counts always match.
- **"AI next step" is on demand only**, never saved or sent: the email draft is copy-paste for a human. Contacts aren't modelled, so drafts are addressed by role. Every ₹ figure in the draft is checked against the deal's data in code and mismatches are flagged; wording and tone are not checked. Verified with one live call (Hooli); quality on other deals untested.
- **Try cases are scripted scenarios on invented clients** (Lumen Foods, Vertex Labs, Helix Pharma, Nimbus Bank, Orbit Telecom). Checklist ticks are computed from live data; look-and-see steps are not auto-verified. AI cases spend real calls from the 50-call budget (about 6–8 to run all four).
- **Dashboard charts are hand-built (no chart library)** from the same data load as everything else. ARR = monthly × 12. Entity filter uses the deal owner's entity, not a field on the deal. Practice filter matches any non-zero share; it does not pro-rate deal value. "Collected" includes payments made after an invoice's deadline. Light mode only.
- **Dashboard Diagnose panel**: groups leak-engine alerts by type, ranked by ₹ at stake, with next steps and actions run in place (analyse, draft brief, AI next-step draft, record payment, log hours, mark partner registered, set practice split). AI actions ask for confirmation and use the 50-call budget; nothing is sent to clients or partners.
- **Dashboard Value panel**: counts (deals corrected at entry, ARR kept out of one-time, deal→brief time, clawback surprises, AI cost) come from live data. "Manual hours saved" is an estimate from stated per-item minutes (30 min per deal fix, 180 per brief, 20 per invoice tracked, 15 per leak found by hand), not measured.
- **Manual Loop walkthroughs on Try cases are illustrative**: hand-written steps and timings based on stated assumptions (month-end forecast review, 1–2 day Slack loops, finance clawback run ~30 days after quarter close), not measured from Devx's real process. They read no pipeline data and make no AI calls. Next: replace with timings measured by running both loops side by side.
- **Leak engine thresholds are invented**: renewal window 90 days, "urgent" = 30 days, margin floor 30%. Leak alerts are rules only (no AI), recomputed on every page load; there are no notifications (email/Slack) yet.
- **AI model is Claude Haiku 4.5**, chosen for cost; quality is backstopped by deterministic validators. AI calls are capped at 50 for the whole project via an `ai_calls` ledger (fails closed; no SDK retries).
- **Demo "today" is 2 Oct 2026** (start of Q4); seeded dates are chosen around it.

## How I used AI tools to build this, and where I overrode them
- **Built with Claude Code** (Claude as a coding agent in VS Code), including parallel sub-agents for the Clawback/Margin and Onboarding modules, each restricted to its own files. I reviewed their reports and re-ran their tests myself.
- **The app uses the Claude API** (Haiku 4.5) for two jobs only: splitting/cleaning deal text, and drafting onboarding briefs.
- **Overrides and corrections:**
  - Rates: the first invented rates made Wayne's cost exceed its price, so I retuned them to realistic levels.
  - Recurring billing: the schedule is generated by code, not the model ("AI drafts language, code owns money schedule").
  - Confidence: the model rated Acme "high"; the validator capped it to "medium" because the 1 Dec start date was assumed. Model confidence is never trusted on its own.
  - Prompt fix after a live run: the onboarding draft read the internal practice split (Web 70 / Cloud 30) as a delivery split with AWS. Practice split is now withheld from that prompt. The fix is not re-verified live (to save API calls).
  - Model: downgraded from Sonnet to Haiku and capped at 50 calls on the account owner's instruction.
  - Indian FY: an agent pointed out that Apr–Mar quarters give the same realization deadlines as calendar quarters; I adopted that framing.

## Schema choices worth flagging
- `people.name`, `deals.name` and `(invoices.deal_id, milestone)` are unique so CSVs can reference records by name instead of UUID. Real system would key on Zoho IDs.
- A DB check constraint enforces "recurring ⇔ has term_months" so a blended record cannot be stored even if the app layer is bypassed.
